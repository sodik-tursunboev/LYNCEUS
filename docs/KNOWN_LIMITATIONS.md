# Known limitations (v0.1: M0 to M3; M4 to M7 added below)

> **Measured on real data (E1, 2026-11-10, `docs/eval/url-real.md`): the URL rules catch 2.5% of real phishing URLs; on 91% of them no URL rule fires at all.** The high figures elsewhere in this repository come from samples written by the same author as the rules. Lynceus catches a new phishing link today mainly when a list (OpenPhish, PhishTank) already has it. On the owner's own browsing 9.2% of 87 URLs were flagged (sign-in pages and redirect parameters).

Written to be read before trusting anything in the repo. "Not verified" means code or config exists that was never run.

## The Windows agent and browser extension (M4): what they are and are not

- **Blocking is "fail open" and asynchronous by default.** The first visit to a URL nobody has judged yet can start loading before the verdict arrives (tens of milliseconds locally); the warning page then replaces it. Only a URL **already judged bad** is stopped before any request is sent, and only after you grant the extension site access on its options page. Measured earlier on 2026-11-05: with the permission granted, a second visit to a bad URL never reached the server (headful Edge, `extension/e2e`); in later runs the browser did not accept the permission request automatically, so that test skips itself in that case; a later run passed it again, so it is intermittent and environment-dependent. Without it, every visit can reach the server first.
- **If the agent is not running, nothing is checked.** Pages open as normal and the toolbar badge shows `!`. A core that is down while the agent is up shows `?`. The agent is started at logon by a per-user Run entry; if you log out, or it crashes, there is no protection until it restarts.
- **Files are flagged; only you (or `auto` mode) move one.** A verdict, a notification and a record; a MALICIOUS file is moved to quarantine only after your click (M6), and can be restored. A file is never BENIGN. Files over 16 MiB are described (name, size, hash, type) but their contents are not opened. A file an antivirus has already blocked cannot be read and is skipped and counted.
- **A download is seen when the folder watcher sees it, not when the browser starts it.** The agent waits until the file has been quiet for a second and can be opened. A file locked for ten minutes is given up on. `FileSystemWatcher` can lose events; every loss triggers a re-scan, and a checkpoint covers restarts, but this is a safety net, not a guarantee. First start looks only at files from then on.
- **The path of each waiting file is kept on disk** (in the agent's data folder, current user only) until it is judged, because the agent has to read the file again to send it. The path is never sent to the core, logged, or stored there.
- **The browser's Mark of the Web holds full URLs.** The agent reads it to take the host and never sends, stores or logs the rest in the core. The one exception is the quarantine record in the agent's own data folder (current user only), which keeps the file's complete mark so that a restore can put it back; it never leaves that folder.
- **Browsers:** tested with the installed Microsoft Edge only (156). Chrome is expected to work (same APIs, the host is registered for both) but is **not verified**. Firefox is not supported. InPrivate/Incognito are off unless you turn them on for the extension.
- **The extension is loaded by hand** (Load unpacked from `extension\dist`) until the M7 installer. The extension ID is pinned by a key in the manifest.
- **Local IPC.** The pipe is current-user only with a per-install secret; a process running as **you** can read that secret and talk to the agent (same trust level as any program you run). Remote pipe clients being refused is **not verified**. The service worker staying alive while a native port is open is **documented but not observed** here (the test harness keeps it alive itself): the worker reconnects every time it starts, so the design does not depend on it.
- **Notifications:** the call succeeds from an unpackaged program (tested); whether a banner is **visible** depends on Focus Assist and Windows settings and is yours to confirm. An elevated agent could not show them.
- **Not tested:** another security product running alongside, a machine with several users, roaming profiles, a non-default Downloads location on a network drive, and the first-run permission prompt a real user sees (headless/headful automation grants it without the prompt).
## Responses and the console (M6): what they are and are not

- **Only files and email, only MALICIOUS.** Suspicious files and messages and URLs are never moved, blocked by this engine or quarantined (the browser warning page is M4; email quarantine is M6b and needs the separate, wider permission, see below). A mis-judged file or message is therefore at most *proposed* for quarantine, and by default only when you press the button.
- **Needs the database.** Responses and the console's lists come from the database; without `LYNCEUS_DATABASE_URL` the verdicts still work but no action is proposed.
- **`auto` mode moves files without asking** (MALICIOUS only, off by default). The verification before the move (same SHA-256 as judged) is strong, but a wrong verdict would still move a harmless file; it is restorable, not lost.
- **Quarantined files are sealed (H1 A7), not destroyed.** Each is encrypted (AES-256, counter mode) under its own key, the key under DPAPI for your Windows user, in `%LOCALAPPDATA%\Lynceus\quarantine\<id>\payload.sealed`: a double-click cannot run it and an antivirus sees noise. A program running as you can still unseal it (same trust as you). If this Windows profile's keys are lost (a reinstall without the profile), a sealed file cannot be restored. There is no purge: disk use only grows until you delete the folder yourself.
- **Another security product can get there first.** If it quarantines or locks a file, the response is FAILED with a reason (`blocked`, `locked`, `missing`), not retried forever. Two products acting on one file was not tested.
- **File symbolic links** could not be tested on this machine (creating one needs a privilege this account lacks); a link to a folder (a junction) is tested. The check is in the code.
- **Restore puts the file back dangerous.** It does not re-scan; the allow-list option stops further proposals for that exact content only.
- **The console runs in a browser tab,** not a native window. It is same-origin with the API behind a strict policy, and other pages in the same browser cannot read its `sessionStorage` because of the browser's origin rules. `Lynceus.Agent.exe --open-console` puts the token in the address fragment once; browsers do not send it to servers, the console removes it from the address bar at once, but the browser's history may keep the first visit. Typing the token avoids that.
- **Not verified:** the console in Chrome or Firefox; screen readers and keyboard-only use beyond the semantic markup used; very large numbers of events (lists are capped at 100 to 200 rows and refresh every few seconds).
- **The Analyze page (UI1)** reads a dropped file in the browser and sends it to the core exactly as the agent does; a pasted message is re-encoded as UTF-8 (drop the `.eml` for an exact analysis); files over 16 MB and messages over 10 MB are refused; its history lasts for the session. Colour contrast was computed (AA in both themes) but the page was **not tested with a screen reader**. See `docs/milestones/UI1.md`.
## Deployment and CI (M7)

- **The installer is unsigned, and the core runs from the checkout.** `deploy\install.ps1` is reproducible and per-user, but it needs the .NET SDK, Node, Python and a checkout on the machine. A per-user WiX MSI is built (`deploy\msi\build-msi.ps1`, ADR-019), also unsigned. Code signing is not done.
- **CI has never run.** The Windows job added in M7 is `continue-on-error` and unverified; whether the sandbox (an AppContainer) works on a hosted runner is unknown.
- **Performance numbers are one machine, one run, a shared desktop.** They are an order of magnitude, not a guarantee. A mailbox burst and a large download backlog were not load-tested.
- **Fuzzing is bounded** (fixed seeds, thousands of cases); it is not coverage-guided and it did not cover the native parsers inside the sandbox beyond the existing fixtures.
## The live mailbox (M5): what it is and is not

- **Never run against real Google.** Everything is tested against a fake Gmail that follows the documented request and response shapes. That proves our logic (de-duplication, recovery, failure handling, read-only enforcement, privacy), not that Google accepts this client, that consent works for your account, or that real raw messages parse. The live checklist is in `docs/milestones/M5.md`.
- **Tokens last 7 days while the Google project is in "Testing" status,** and die on a password change. The status shows `reauth_needed` and the agent notifies once; you reconnect with `python -m core.mailbox connect`. `gmail.readonly` is a restricted scope: making this permanent for others would need Google's verification and a security assessment, which this project does not pursue.
- **Outlook is built the same way and is just as unproven.** The Microsoft Graph client (M5b) is tested against a fake Graph only. Not verified: that Microsoft accepts this client, whether `Mail.Read` needs administrator consent on your work account, how long a delta token lives and which error an old one returns (HTTP 410 and 404 are both treated as "re-read the last days"), Outlook's real throttling numbers. It reads the inbox folder only, not other folders. `disconnect --provider outlook` removes the local token; remove the app's access in your Microsoft account's app-permissions page. No IMAP.
- **Read-only means read-only, until you give the separate write permission (M6b):** with only the normal sign-in nothing is labelled, moved, deleted or marked read. A flagged email stays in the inbox; you get a notification (rule names, a score, no sender or subject because the engine never reports them).
- **Mail that is missed.** The poller looks back N days (default 2) on first connect and after an expired history position, polls every 60 s, and handles about 100 messages a minute (quota). A larger burst is queued over several polls; a message that arrives and is deleted inside one poll interval can be gone before it is fetched (counted as vanished, not analysed). Whether `messageAdded` also covers mail that arrives already read is not stated in Google's pages that were read; the re-list covers it at a quota cost.
- **One parser at a time.** The poller analyses messages one by one in its own thread; it does not share the API's parser slots.
- **A message over 10 MiB** is stored as UNKNOWN (`too_large`), not opened.
- **Local trust:** a process running as you can decrypt the stored refresh token with DPAPI. `python -m core.mailbox disconnect` deletes it and asks Google to revoke it; revoking in your Google account does the same.
## Email quarantine (M6b): what it is and is not

- **Never run against real Google or Microsoft.** The movers and the runner are tested against fakes that follow the documented shapes (labels, `messages.modify`, folders, `move`). That proves our logic and the request guard, not that the providers accept these calls, that the consent works for your account, or what a real mailbox does. The live checklist is in `docs/milestones/M6b.md`.
- **The permission is wider than Lynceus's use of it.** `gmail.modify` is described by Google as read, compose and send (it excludes permanent delete); `Mail.ReadWrite` can delete mail (it cannot send). Lynceus's own code is held to a handful of requests by a guard and cannot delete or send, but a program running as you can decrypt the stored token and is not held by it. Withdraw it with `python -m core.mailbox disconnect --write`.
- **Google's restricted scope:** while the Google project is in "Testing" status tokens last 7 days; whether a Testing-status app gets `gmail.modify` for its own account was not verifiable from the documentation. Public use would need Google's verification, which this project does not pursue.
- **Only MALICIOUS mail, only on your click, only the inbox.** SUSPICIOUS mail and other folders are never touched; `auto` mode cannot approve a mail move. The write permission must exist when the message is judged: mail judged before you gave it is not proposed later (connect, then a re-read of the last days finds nothing new because those messages are already seen).
- **A message can be left behind by a crash.** A crash between Outlook's reply and the database commit leaves the message in the `Lynceus Quarantine` folder with the action FAILED (`message_gone`): nothing is lost, move it back by hand. A crash between marking a message seen and proposing its action means no proposal for that message (its verdict is stored).
- **A moved message is not quarantined in any stronger sense.** It sits in a label or folder in your own mailbox, readable and clickable; Gmail keeps it searchable. Restore is one click; there is no purge.
- **Unverified, treated conservatively:** what Gmail does on a duplicate label name, whether `modify` repeats safely, whether Graph accepts `inbox` as a `destinationId` (the real inbox id is resolved first), `$filter` on folder names (matched in code), whether the message id changes on a Graph move (assumed yes; both cases handled).
- **The migration (`0003`) passes on SQLite and on real PostgreSQL** (upgrade from `0002` with data, downgrade, schema matches the models).

## Threat intelligence (M3): what it is and is not
- **No adapter has been run against its live service.** They are built from the providers' documentation and tested against synthetic fixtures and a mock transport. Unverified: the URLhaus export path and CSV layout, PhishTank registration and rate limits, VirusTotal's domain-object field names and Terms of Service, RDAP registries' rate limits and query logging. A wrong assumption about a reply shape shows up as a stated provider ERROR, never as a wrong verdict, but the first real run will probably need fixes. You must register for the keys (VirusTotal, PhishTank, URLhaus) yourself.
- **The real-world value of the providers is unmeasured.** The corpus is synthetic and its hosts are unregisterable, so no listed URL or young domain can be in it; the eval is unchanged by M3. Whether list feeds, domain age or VirusTotal add detection, and how many false positives they add, is unknown until they run on real traffic. Decision D8 (measuring the URL rules on a downloaded PhishTank snapshot kept outside git) is still open for you to run.
- **Terms limit what v0.1 may be.** VirusTotal's public API, Safe Browsing, OpenPhish's community feed, URLhaus and urlscan's free tier restrict use in a product or business. v0.1 is a single person's local, non-commercial tool; distributing it needs commercial terms for each provider (ADR-015).
- **Query providers do tell someone something.** With RDAP or VirusTotal on, the registered domain of each URL you analyse reaches a registry or VirusTotal (which says it adds queried indicators to its public dataset), along with your IP address and, for VirusTotal, your account. Only a public registered domain is sent, never a path or a token, and it is off by default, but it is still a record of the sites you looked at. **Since DA2 an established site (Tranco's top 100,000, a brand's own domain) is never sent**, which removes most of what a person browses; every other site you visit still is. Message links stay local unless you set `LYNCEUS_INTEL_EMAIL_LINKS`.
- **File reputation sends a hash (DA2, off by default).** With `LYNCEUS_FILE_REPUTATION=true` the SHA-256 of each downloaded program-like file (programs, installers, scripts, shortcuts, disk images, archives, macro-enabled Office files; never PDFs, pictures, documents) goes to VirusTotal, which adds queried indicators to its public dataset: it learns that this file exists on a computer using your key. A file renamed to a document type (a program called `invoice.pdf`) is not asked about, because the choice is made from the name. "VirusTotal has no report" proves nothing and changes nothing; so does any failure or the free key's limit (4 a minute, 500 a day, shared with the domain lookups). Many engines flagging a hash is treated as exact identification: a small engine's or a vendor's false positive on a rare legitimate program would then quarantine-propose it (a click is still needed; the thresholds are in `docs/eval/filerep.md`). The free key may not be used in commercial products.
- **Feeds are third-party data, hours old.** A list is only as current as the last `sync` (PhishTank hourly at best, OpenPhish every 12 hours); a list older than its limit reports UNAVAILABLE. Entries are exact URL matches, so a phishing page moved to a new path is invisible until it is listed; a listed host with other paths is a weak signal (and ignored for shared platforms). Phishing kits that show scanners something else are not helped by any of this.
- **A listing is evidence, not proof.** One provider alone gives SUSPICIOUS (WARN). PhishTank and URLhaus entries can be wrong or stale; urlscan's own FAQ warns against unattended blocking on provider verdicts. Nothing here ever produces BENIGN.
- **State is in memory.** The cache and the rate-limit counters reset on restart (a restart can spend part of VirusTotal's 500 a day twice). The circuit breaker is per process.
- **Keys can still be plain text in `.env`** if you leave them there: `python -m core.secrets set NAME` stores them under DPAPI instead (H1 A4) and the core warns at start, by name, about any left in `.env`. PhishTank and URLhaus keys travel in the download URL (hidden from logs and results, visible to the provider and any proxy).
- **Not built:** urlscan (deferred to an on-demand investigation feature), Web Risk (needs billing), Safe Browsing v5 (the stretch goal), OCR (M2). The email ruleset has no explicit caps for `link.intel.*`.

## What the M2a message engine cannot do (MIME, headers, HTML, links, attachment inventory)
- **What is opened:** PDFs, zip/tar/gz/bz2/xz archives, and png/jpeg/gif/bmp/tiff/webp images (QR codes), each in its own sandbox process, up to 8 attachments per message (the rest are reported as `skipped`). **Not opened:** 7z, rar and iso (named only), Office documents (out of M2: macro-enabled files are flagged by name and type, never read), password-protected archives and PDFs (reported, contents unknown), and anything else.
- **No OCR (deferred by decision, ADR-004).** Text inside images is not read. A phishing lure that is only a screenshot with a typed URL is invisible; a QR code is decoded.
- **PDF triage is features, not behaviour.** It counts JavaScript, Launch, embedded files and link annotations through qpdf, and (H1 C4) reads links written out in the text of the first 30 pages. It does not render: a link hidden under an image, a form that posts elsewhere, content in an XFA template, and text in a font with its own encoding (common in generated PDFs) are only as visible as the dictionary entries.
- **QR decoding is OpenCV's detector, tuned on synthetic codes.** Real photographs, tilted, low-contrast or logo-overlaid codes will be missed; on a miss the image is simply a clean image. A QR code to a login-looking domain with no brand and no other signal was UNKNOWN (dev sample `m2b-025`; since AI1 the learned domain model catches that one), and a PDF whose only feature is an embedded file is UNKNOWN (`m2b-018`): both are counted as misses.
- **Archive limits are declared, not measured.** A bomb is recognised from headers and a read budget (48 MiB); a malicious archive that stays under the thresholds (256 MiB declared and 100x expansion) is just an archive. Entry names and contents are never kept; only extensions, real types and counts reach the rules.
- **HTML smuggling is pattern counting** (`new Blob`, `atob`, large base64, `download` on a data link) on the first 200,000 characters of script. Heavy obfuscation, string splitting or loading the payload from a remote file defeats it.
- **Cost.** Each opened attachment starts a sandbox; importing the image libraries takes about 3 seconds cold. A message with several attachments takes seconds, not milliseconds, and the sandbox folder is about 208 MB.
- **A message is never BENIGN** (ADR-014). The best a clean message gets is UNKNOWN. That is correct and also means there is no "this is fine" answer to show a user.
- **CSS is read on the element and in `<style>` blocks, simply (H1 C1).** Inline styles and top-level `<style>` rules with simple selectors (`tag`, `.class`, `#id`, `tag.class`, `tag#id`) are cascaded by specificity, inline winning. Not read: rules inside `@media` (on purpose: responsive mail hides parts on one screen size), any selector a media query also names, descendant or attribute selectors, linked stylesheets, and a `<style>` block that comes after the element it hides. Text and link order are not rendered, so overlaid or reordered text can fool the link-text rules.
- **Link text is compared to its target only for anchors,** and only when the text contains something that parses as a domain with a known suffix. "Click here" over a bad link is not a mismatch; it is still analysed as a link.
- **Relative links are skipped** unless the message sets `<base href>` (counted in the report as `relative_links_skipped`). Past 100 distinct links the rest are counted, not analysed. Past 500 links, or 2 MiB of HTML, or 50,000 tags, the scan stops and says so (`limits_hit`).
- **`Authentication-Results` is read from the topmost header only, and only its failures count.** A sender can forge a lower copy saying `pass`, but no rule ever uses a pass to lower a score, so a forgery changes nothing (checked for H1 C3). Nothing is recomputed (no DNS, by design): a provider that adds no header gives no authentication result at all.
- **Brand and sender checks inherit the M1 gaps:** an unverified brand list, and no typosquat/combosquat catch for a digit-swapped brand plus keyword (`paypa1-secure.test`): the M1 rules were left alone after the holdout was spent.
- **Non-English coverage is thin:** urgency and credential phrases are English and Polish only, from general knowledge, not measured.
- **Storage keeps hosts in plaintext** (`domains`), so the database records which sites a user's mail linked to. No message text, URL, address or file name is stored (a test scans every table), and ADR-007 is still unsigned.

## How far the message numbers can be trusted (M2)
- 180 synthetic messages from templates (dev 119, holdout 35, reserve 26), written by the author of the rules. **They measure rule correctness, not detection of real phishing.** No real mailbox, phishing feed or authorized dataset was used.
- **Dev (not tuned beyond writing the rules, `docs/eval/mail-dev.md`):** TP 72, FP 0, FN 2, precision 1.000 (95% interval 0.949 to 1.000), recall 0.973 (0.907 to 0.993) counting abstentions as misses. Both misses are documented hard cases. **All 45 benign messages are UNKNOWN, never BENIGN** (abstain rate 0.395): a message gets no allowlist, so a flag rate of 0 shows that nothing benign was flagged, not that anything was recognised as safe.
- **Holdout, run once on 2026-11-05, logged in `docs/eval/mail_holdout_runs.md` (`docs/eval/mail-holdout.md`):** n = 35, TP 22, FP 0, FN 0, recall 1.000 (95% interval 0.851 to 1.000). 12 of the 35 (the attachment messages, `m2c-*`) were written blind to the rules and the other 23 come with the first corpus, but all 35 share templates with dev, so a perfect score is what shared templates predict; it is not evidence of 100% real-world recall. The reserve (26) has never been run.
- **24 rules have no hit on dev** (12 message rules, among them archive traversal, image bomb, XFA, link flood, meta refresh, the typosquat/homograph sender rules and `file_inspection_incomplete`, and 12 URL rules). They pass their positive and negative test messages but have no corpus coverage, so their weights are untested guesses.
- Latency (p50 about 0.35 s, p95 about 1.1 s) includes starting the sandbox once or more per message on a shared machine; order of magnitude only.

## What the sandbox does not cover
- **Windows only.** The restricted process (AppContainer plus Job Object) is Windows-specific; on any other system analysis returns ERROR `sandbox_unavailable`, and the sandbox tests are skipped. A Linux container route is not built. The parser libraries are pinned to Windows x64 / CPython 3.14 wheels (`requirements-sandbox.txt`).
- **Native parsers are the new attack surface:** qpdf, libxml2 (through lxml), Pillow's decoders, OpenCV and numpy now run on attacker bytes. They are inside the sandbox, on pinned versions, with the FFmpeg plugin removed, and fuzzed here only by random-bytes tests; they have not been audited or run under a fuzzer.
- **Concurrency is up to 4 requests x 4 sandboxes** (one parse plus 3 attachment inspections each), 16 processes at most.
- **Per-user setup.** Building registers an AppContainer profile (`python tasks.py sandbox`; `python -m core.sandbox.build --remove` undoes it). The sandbox is rebuilt from scratch each time, and a stale copy is caught by a test, not by the runtime.
- **It is a mitigation, not a proof.** Kernel or interpreter escapes are out of scope; the limits are memory, CPU time, wall time, output size and one process. A hostile message can still burn those limits (and does, by design, end as UNKNOWN with a reason).
- **Concurrency is capped at 4 requests** (`LYNCEUS_MAX_CONCURRENT_PARSERS`); a fifth waits one second, then gets 503.

## What the M1 engine cannot catch
- **It sees only the URL string.** No reputation, domain age, WHOIS, page content, meta-refresh or JavaScript redirects, QR codes, email or files. A freshly registered phishing domain with no brand name or keyword in it is UNKNOWN, never BENIGN.
- **It rarely says MALICIOUS on its own.** MALICIOUS needs two independent strong categories (ADR-013). On the synthetic corpus 13 of 87 malicious dev samples and 3 of 30 malicious holdout samples reached it; the rest are SUSPICIOUS, which recommends WARN, not BLOCK. Blocking confidence has to come from threat-intel providers (M3).
- **Shorteners are unknowable offline.** The one holdout miss is a shortener. Following redirects would help, but the resolver is off (below).
- **The brand list is general knowledge, not verified.** 105 brands, Polish and global; every entry is `verified = false`. A wrong official domain means a false positive or a wrongly BENIGN fake. Only listed brands are protected; there are no non-Latin brands, and keywords are ASCII only.
- **UNKNOWN is common by design:** 32% of dev and 26% of holdout. On benign samples it means "no rule fired", not "safe".
- **Edit-distance matching can flag ordinary words** near a brand name. `not_typos` and `fuzzy = false` cover the cases found so far; the corpus has 0 false positives, but it was written by the rule author.
- **Script detection is approximate** (Unicode character names, not the Scripts table). It separates Latin, Cyrillic and Greek well; rarer pairs are unproven.
- **`url.credential_bait` never fired** on either split. It passes its fixtures but has no corpus coverage.

## How far the numbers can be trusted
- 253 synthetic URLs from seeded templates (150 dev, 49 holdout, 54 sealed reserve), written by the same author as the rules. **They measure rule correctness, not the real-world detection rate.** The holdout shares the dev templates, so it tests new brands and variants, not new attack styles; it came out like dev (precision 1.000, recall 0.967), which is what shared templates predict.
- The holdout was run **once**, on 2026-11-04, and logged in `docs/eval/holdout_runs.md`. Nothing in the rules or data changed afterwards. It has 49 samples, so recall's 95% interval is 0.833 to 0.994.
- A holdout failure should be fixed by moving those samples to dev and drawing a new holdout from the reserve. The reserve has never been run.
- **Latency is an order of magnitude, not a benchmark.** The same code measured 1.4 ms and 14 ms p50 on the same machine hours apart (A/B of old and new commits, no regression). `url.typosquat` is about two thirds of analysis time.
- Parser: 554 of 560 WPT cases match; the 6 differences are deliberate (ADR-012). 320,000 fuzzed inputs produced no exception.

## Security gaps
- **No URL text is stored** (decision D2), and since H1 A8 (ADR-007) no site name either: hosts, rule descriptions, evidence summaries and explanations are sealed with DPAPI for your Windows user, and lookups use a keyed hash. Limits: audit rows written before the upgrade keep the host they named (they are append-only); the console and `core.export` show hosts in clear to whoever runs them as you; if this Windows profile's keys are lost, stored site names read as "(sealed by another Windows user)". Nothing writes `evidence_payloads`.
- **Audit records are append-only in the database** (H1 A2): a trigger refuses UPDATE, DELETE and TRUNCATE on `audit_logs`. Responses, overrides, feedback, console sign-ins, failed sign-ins (counted per minute) and page detonations are recorded. Plain analysis calls are not. The database owner can still drop the trigger: that is a schema change, not a quiet edit.
- **API access:** the agent holds the API token; the console holds only a session of its own (H1 A1, 12 hours, ends on sign-out or a core restart) and acts only as the person. No rotation of the API token, a per-process rate limit, loopback only and no TLS. `/health` is open.
- **The redirect resolver is off and unwired** (ADR-011, draft). The guard has 151 offline tests, 13 mutation checks and a manual live run. Not verified: IPv6-only networks, corporate proxies, TLS-inspecting firewalls, DNS-over-HTTPS. A resolved chain is never proof of safety: phishing kits show scanners something else.
- Log redaction is pattern-based and tested on known patterns only. Python dependencies install from the hash-locked `pylock.toml` (H1 A5; Windows, CPython 3.14 wheels only; checked in a fresh environment on 2026-11-14, but pip 26.2 still calls installing from a `pylock.toml` experimental, so a later pip may need the lock exported to a hashed requirements file); the console's and extension's npm packages are locked by `package-lock.json`, the agent's NuGet packages by version.

## Not verified
- **CI has never run.** There is no remote. Its steps are the commands that pass locally. It has no PostgreSQL service, so the PostgreSQL tests would skip there. This is the one open item in M0.
- **Python 3.12 and Linux/macOS.** Everything ran on Windows 11 with Python 3.14.7. The `ada-url` wheels for Linux and 3.12 exist but were only downloaded, not run.
- PostgreSQL 17 is verified locally through Docker (migrations, the store, and the API with a real uvicorn). No Docker in CI.

## Tooling and process
- The git hook must be enabled once per clone (`python tasks.py hooks`). Git for Windows' `sh` cannot fork on this machine, which is why hooks are plain `.githooks`.
- pytest prints a Starlette deprecation warning about `TestClient` and `httpx` (ADR-004).
- Tests block non-loopback network use (`tests/conftest.py`); the manual live test turns the block off on purpose.
- ADR-007 (evidence encryption) is unsigned; ADR-008 to ADR-011 were decided by the owner as recorded in `docs/DECISIONS.md`.

## Found by the independent review (R1, 2026-11-06): what remains after the fixes
Two reviewers who had not seen the code before read it adversarially; `docs/milestones/R1.md` lists every finding and what happened to it. These are the ones that are **not fully closed**:

- **The checkout can be changed by other accounts on this machine.** Confirmed with `icacls`: a folder made directly under `C:\` inherits "Authenticated Users: Modify". The core runs from the checkout with your rights and your token, so on a computer with a second account, that account could run code as you. `deploy\install.ps1` now **warns** and `-HardenAcl` restricts the folder to you, SYSTEM and Administrators (tested on a temporary folder; it was not applied to your checkout). On a computer only you use this does not matter.
- **Pages loaded inside frames are never checked.** Only the top-level page is judged and redirected, so a clean wrapper page can frame a lookalike page. Judging sub-frames means a core check for every ad and embed; not done.
- **A flood of distinct URLs can still make URL checks fail open.** The URL check now has its own much larger rate limit (1,200 a minute) so it cannot starve file checks, but a page that bounces through enough distinct URLs can still push the core to answer "busy", and then the next page loads unchecked with a `?` on the toolbar icon.
- **The agent's API token still does everything.** Since H1 A1 the console has its own session that can only act as you (never `policy`, never report what the agent did), and `--open-console` puts a one-time code in the address, not the token. But the extension talks through the agent, and whoever reads the agent's token (a process running as you) can still do anything.
- **A quarantine record is flushed to disk, but power loss was not tested** (it cannot be on this machine).
- **Graph:** one message id outside the expected shape makes the sync stop with a stated `bad_response` error until it is fixed, rather than skipping that message. That is deliberate: a skipped message would be mail nobody looked at.
- **Mail backlog:** a burst is read over several polls without losing position, but more than 5,000 unread messages in one range can cause the oldest to be read again (the list of already-read ids is capped at 5,000).
- **The HTML scanner reads one level of Outlook conditional comments and VML links,** `formaction`, `embed` and `object`; it still does not treat images, style sheets, media or `<a ping>` as links.

## Macros read as programs, and the local model (ADR-023)

- **Measured on synthetic macros only.** Every macro in the tests was written for them, to published file layouts. No real Office file and no real malware has been through this analysis. The corpus numbers (8 of 8 unknown-malicious macros flagged, 7 MALICIOUS; 0 of 10 ordinary ones firing a new rule) show the design works as intended, not how it does in the wild.
- **The evaluator runs only the macro's own text-building code.** It does not model objects (`Collection`, `Dictionary`, class modules, `With` targets), `GoTo`/`GoSub`, `On Error` flow, `Like`, user-defined types or dates. A command built from cells, form captions or document properties exists only in the real document, so it is reported as "reads from a hidden store", not spelled out.
- **Excel 4.0 macros in old binary workbooks (`.xls`):** the macro sheet, whether it is hidden and the built-in `Auto_Open` name are found; the formulas themselves are not read. In `.xlsm` (XML) they are.
- **P-code is compared with the source by its readable text,** not disassembled. Password-protected (encrypted) documents are not opened.
- **The local model is advice, off by default.** On `llama3.2:3b` it answered all 24 test macros in the fixed form and agreed with all of them, but only 6 of those were written independently of its briefing; six is a small number. It runs only on files the agent or the Analyze page send and on messages posted to the API, **not** in the mailbox poller. A first answer after the model has been idle can take 15 to 35 seconds; past 45 seconds a verdict goes out without it.
- **What the model sees:** the macro's code (comments removed) and the strings its decoders build, sent to `127.0.0.1` only. It is not stored. Whatever the model says, a verdict can go up by at most one weak signal, never down, and never to MALICIOUS on the model's word.

## Learned and local-model judgment (AI1)

- **The learned domain model reads the registered domain only.** It cannot see a brand in a subdomain or a trick in the path (the rules do), and a phishing page on a domain that looks ordinary passes it. Measured on unseen domains (`docs/eval/learned-url.md`): it lifts fresh-phishing catches several-fold (PhishTank 1.6% to 17.1%, D1 live pages 12.2% to 54.0%) at 0.3 to 0.8% false alarms on the legitimate sets, but the legitimate samples with real subdomains and paths are small (your browsing 0 of 86, D1 legitimate 2 of 259). It was trained on 2024 to 2026 data; phishing names drift, so it needs re-training. A long hyphenated legitimate name (one synthetic hard negative) can be flagged. In mail its weight is lower (0.3) and it needs a second sign.
- **The brain is built but not measured.** Its weights are provisional and it is off by default; it waits for the end of the study's rewrite run (same graphics card). A small local model is often wrong: every claim is checked against the page, its code or the message before it counts, but a checked claim can still be a wrong judgment (for example, a real partner page that names a brand it works with). It is slow here (one RTX 2050): it judges opened pages and mail in the background, never the browser's instant check.
- **The brain can be steered toward silence.** A page or message can talk the model out of a finding; that costs a missed finding, never a lowered verdict. Talking it INTO a false finding needs text that is really on the page plus a domain the brand does not own.
- **The script brain needs detonator image 1.1.0** (not yet built), which returns the page's own code (12,000 characters, third-party libraries left out).

## Deeper analysis and fewer false alarms (DA1, `docs/milestones/DA1.md`)

- **About 1 in 40 ordinary small sites still gets a warning from its address alone.** On 3,000 long-tail sites (Tranco ranks 100,001 to 1,000,000, off the popular list) the address rules plus the learned model flagged 2.4% (72), against 2.5% before DA1, almost all of them real small sites whose names look like phishing names. A two-level model (the model counts alone only above a stricter level) cut the long-tail rate by a third on one sample (2.0% to 1.3% of the same 3,000 sites) but caught 1.6 to 6.1 points less phishing (PhishTank 18.5% to 16.9%, PhiUSIIL 35.4% to 32.1%, D1 live pages 61.5% to 55.4%), so it was not adopted. With the page opened, 2 of 103 alive long-tail pages (1.9%, 0.5 to 6.8) were flagged.
- **Most live phishing cannot be read.** Of 183 phishing pages opened hours after their feed was published, 45 (24.6%) were still alive and 101 answered the sandbox with a refusal (HTTP 403: cloaking, region blocks, bot checks). Nothing a page rule reads exists on those.
- **A second look at a near-empty page found nothing to gain in this run** (0 of 45 alive phishing pages needed it, 3 of 185 legitimate did): kept because it costs 5 seconds only on near-empty pages, unproven.
- **Certificate age is evidence only (weight 0).** A certificate under 7 days old on a sign-in page was seen on 2 of 45 alive phishing pages and 0 of 185 legitimate: too few to set a weight.
- **The typosquat and brand-in-domain changes are small.** On E1's test split, legitimate flagged went 56 to 51 of 40,685 and phishing flagged 11,352 to 11,347 of 30,090 (inside the noise); the brand-in-domain change removes 28% of its legitimate hits and 3% of its phishing hits but changes no verdict, only the evidence shown.
- **Windows installers** you download weigh 0.3 as programs, not 0.75: an installer from an ordinary site is no longer SUSPICIOUS by itself (a `.scr`, `.bat`, `.vbs`, `.hta` or a disguised program still is). An installer from a site whose own address looks like phishing still is.
- **Domain age (RDAP) is on since 2026-11-17** (`docs/eval/rdap-age.md`: under 30 days old, 32.6% of phishing domains and 0 of 185 ordinary sites). A legitimate brand-new site would look young too and was not in the sample; about a quarter of domains return no age because their registry has no RDAP server.

## What a phishing author can change, and how fast the model ages (DA3, `docs/milestones/DA3.md`)

- **A cheap ending carries about two thirds of what the address engine catches.** Of the 15,132 test phishing addresses it flags, moving the same name to `.com` leaves 35.0% flagged (`docs/eval/evasion.md`). Plain http, a `www.` subdomain, a harmless query, a longer path and a digit on the name leave 98 to 100% flagged; removing hyphens leaves 91.0%. A phisher who buys a `.com` name defeats most of the address-only check; domain age, the page opened in the sandbox and the known-bad lists still apply to them.
- **The learned model loses about 13 points on current phishing if it is not retrained.** A model that never saw the 2026 feeds caught 55.1% of PhishTank's 2026 phishing domains, the shipped one 68.2%, at the same 0.4% false alarms on legitimate names (`docs/eval/drift.md`). Re-train every few months from fresh feeds.

## Fewer false alarms on popular sites, and feedback (H1 B1, B3)

- **The popular-domain list is a research list.** `python -m core.intel popular sync` downloads Tranco's top 100,000; the look-alike rules that judge a registered name (typosquat, combosquat, brand in domain) stay silent on those domains. Tranco is for non-commercial use, and a rank can be bought with fake traffic at the low end: a long-lived phishing domain that reached the top 100,000 would no longer be called a look-alike (the lists, the page rules and the subdomain rules still see it). Without a sync nothing changes.
- **What it fixed, measured (`docs/eval/popular.md`):** the look-alike false alarms on brands' own country sites and domains (google.no, amazon.ca, discordapp.com) are gone; on legitimate URLs outside the list nothing changes (PhiUSIIL legitimate test 27 to 20 of 40,685). The cost: one live phishing page of 89 in the D1 test half (42.7% to 41.6%) and 3 of about 44,000 E1 phishing URLs. Figures on legitimate sets drawn from Tranco itself are circular and are reported apart.
- **Feedback stays on this computer.** "Was this right?" in the console and "This warning is wrong" on the warning page store your label per verdict and count false alarms per rule; nothing changes a weight by itself. Tuning a rule from it is still a written change with a measurement.
- **Email false alarms are not measured on real mail yet** (H1 B2 waits for your Gmail connection).

## Opening pages in the sandbox (D1, ADR-025)

- **Automatic opening is on for browser links since 2026-11-17 (DA1 P3, the owner's decision).** With `LYNCEUS_AUTO_DETONATION=browser,mail` a link whose address is SUSPICIOUS, or UNKNOWN with a sign, is opened in the background (off the brands' domains and the popular list; each address once an hour, 8 waiting, 2 at once). The browser's first answer does not wait for it: the deeper verdict reaches the next check of the same address and the Events page, not the page already open. A second visit can use up a one-time link, and opening an emailed link can tell the sender the address is read (the owner accepted both on 2026-11-16). Its 14 tests use a fake detonator, and on 2026-11-17 it was run end to end with the real container on public risky-looking sites (a dead page and a live one; the container cannot reach a page served on this computer, by design, and no live phishing link was opened through it). When a page cannot be opened (Docker stopped), the address verdict stands unchanged and the audit log records the page status; the warning page does not say "page not analysed" for a browser check. Without the setting, "Open in sandbox" (or `core.cli detonate`) is the only way a page is opened.
- **The visit comes from your internet connection.** The site sees your IP address. A kit that shows scanners something else (cloaking by IP, by headless-browser tells, by timing, by a bot check before the page) defeats it; the detonator uses a normal Chrome user agent and waits about 4 seconds, nothing more.
- **Needs Docker Desktop running** and the 3.5 GB image. Without them the result says "page not analysed" and the URL verdict stands.
- **A container escape** would land in Docker Desktop's Linux VM, which also runs the PostgreSQL container. A dedicated VM for detonation is not built.
- **The page rules read what the page claims**: a title, headings, logo text, forms, and since H1 C5 the forms inside the first ten frames, from any site. A brand drawn only as a picture with no text, or a brand that is not on the brand list, is not recognised (a vision model for that is D1b).
- **Cloaking (H1 C5):** when the desktop visit gets a refusal, a blank page or a bot check, the page is opened once more as a phone, but only when the first visit ended within 9 seconds (both must fit the 26-second watchdog). A bot check is named (`page.cloaked`) but carries no weight yet: many real sites show one to a headless browser, and next to `url.login_path` any weight would flag them. The frame reading and the phone visit are in image 1.1.0 and are not yet measured on live pages (needs Docker and a new run).
- **One page at a time per container, three at once**; about 5 to 10 seconds per page.
- **Measured on live pages (`docs/eval/detonate.md`, test half): 37.3% of live phishing pages caught with the page, against 16.9% from the address alone; 63% of live phishing pages still pass** (no brand in the title, no form yet, cloaking, brands not listed, generic kits on new domains). Legitimate pages: 3.8% flagged, nearly all by the URL typosquat and login-path rules; the page rules added 1 of 186. The page rules were tuned on the dev half, where their first version flagged 14% of legitimate pages.

## Installing from inside another app (ADR-024)

- **A terminal inside a packaged (MSIX) app writes to a private copy of your registry.** An install run from there looks registered and is not: start-at-logon, the browser bridge and the sandbox profile never reach Windows. This happened to this project's own cutover on 2026-11-07 and left the machine unprotected until 2026-11-10. `install.ps1` and `go-live.ps1` now refuse to run from such a window and check Windows' own view (through WMI) afterwards. `Lynceus.Agent.exe --status` still reads the registry as the calling process sees it. The MSI's setup step was not given the check (Windows Installer is expected to run it outside the calling app; **not verified**).
