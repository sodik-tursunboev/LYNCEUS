# E1: Measure Lynceus on real data

**Decisions (owner, 2026-11-10):** download PhiUSIIL, fresh OpenPhish + PhishTank, and Tranco top 1M; read the Edge browsing history once, locally, counts only; measure, then fit the weights; URLs now, email and attachments later.

**Why:** every number so far comes from samples written by the same author as the rules (see `docs/eval/dev.md`: "synthetic positives measure rule correctness, not the real-world detection rate"). Until Lynceus is measured on data nobody here wrote, no claim about how well it detects phishing is honest, and no upgrade (URL detonation, visual matching, sender profiling) can be shown to help.

**Rule for the whole milestone:** real phishing URLs are handled as **text only**. Nothing in E1 opens, fetches or resolves them. The datasets are kept outside git (`.data/eval/`, git-ignored), each with its source, licence, download date and SHA-256 written next to it.

## Phase A: URLs (this milestone)

**Data (each download needs the owner's OK, see the decisions below):**

| Set | What | Source and terms | Size |
|---|---|---|---|
| PhiUSIIL | 100,945 phishing + 134,850 legitimate URLs, labelled, from a 2024 peer-reviewed paper | UCI ML Repository dataset 967, **CC BY 4.0** (attribution: Prasad and Chandra, Computers & Security, 2024) | the server does not state it; expected tens of MB |
| Fresh phishing | today's OpenPhish (about 300) and PhishTank (about 48,000) URLs | the same feeds Lynceus already uses with the owner's authorisation (ADR-022); this time kept as text so the URL rules can be measured on them | OpenPhish under 0.1 MB; PhishTank about 10 MB compressed |
| Tranco top 1M | popular legitimate domains | tranco-list.eu, a research list; its terms are read from the site before use (the upstream Cloudflare data is non-commercial) | 9.2 MB |
| Your own browsing history (optional) | real legitimate URLs **with paths** (the other legitimate sets are mostly home pages, which makes any lexical detector look better than it is) | read once from Edge's local history file, on this computer only; only counts and per-rule numbers are stored, never the URLs | none (local) |

**What is measured** (the existing `eval/` harness, extended with a `--kind url-real` run):
1. Recall per source (PhiUSIIL, OpenPhish, PhishTank), with Wilson 95% intervals; UNKNOWN counted as a miss, never as "safe".
2. False-alarm rate on legitimate URLs, **split into home pages and URLs with paths**, so the home-page bias is visible instead of hidden.
3. Per-rule precision on real data: which rules earn their weight and which only fire on our own samples.
4. **The lexical ceiling:** the share of real phishing URLs on which no URL rule can fire at all (a plain-looking URL on a hacked or free-hosting site). That number says how much URL detonation (upgrade P1-3) is worth before it is built.
5. A breakdown of misses by kind: free hosting and site builders, URL shorteners, IP addresses, punycode, trusted platforms (SharePoint, Google Docs, IPFS, pages.dev ...).

**Splits:** train / test / reserve by hash, fixed seed, written down before any number is looked at. PhiUSIIL is older than the live feeds, so "fresh" (this week's feeds) is reported apart from "historical".

## Phase B (after A): fit the weights on the training split

A logistic regression over the rule outputs (still one readable weight per rule, so every verdict stays explainable), fitted on train only, compared with today's hand-set weights on test. Pure Python, no new dependency. Adopted only if it is better on the test split with intervals that do not overlap; otherwise recorded and dropped. The two-category rule for MALICIOUS stays.

## Later milestones (not E1)

- **Email** on real data: public corpora (SpamAssassin ham, Nazario phishing) have unclear licences (SpamAssassin: "offered as a service to spam filter developers", no formal licence found; Nazario: terms not found). The better source is your own mailbox, read-only, kept local, which needs the live Gmail or Outlook connection that was never run.
- **Attachments and macros** on real malware: MalwareBazaar samples (your own abuse.ch key), kept zipped and read only inside the sandbox. Needs its own handling plan; the antivirus will react to them.

## Security and privacy

- No URL from these sets is opened, resolved or sent anywhere; a test checks that the evaluation code imports no network module (`tests/unit/test_no_stray_network.py` already enforces it for `eval/`, except `eval/perf.py`).
- Browser history (if allowed) is read from a copy of Edge's `History` file, never uploaded, never written to the database; the report holds counts only.
- The phishing URLs on disk are live attacker links: the files carry a `.txt.gz` name, sit outside git, and are never opened by a browser.

Sources: [PhiUSIIL on UCI](https://archive.ics.uci.edu/dataset/967/phiusiil+phishing+url+dataset), [Tranco](https://tranco-list.eu/), [SpamAssassin public corpus readme](https://spamassassin.apache.org/old/publiccorpus/readme.html), [PhishTank developer info](https://data.phishtank.com/developer_info.php).

## Result (phase A and B, 2026-11-10): `docs/eval/url-real.md`

Run: `python -m eval.realurl` (offline; about five minutes on this machine). 299,460 URLs in the train and test splits; the reserve split (33,462) is sealed. Every figure has its Wilson 95% interval in the report.

- **The URL rules catch 2.5% of real phishing URLs** (133,195): 3.2% of this week's PhishTank and OpenPhish URLs, 2.2% of PhiUSIIL's. Only 0.2% reach MALICIOUS. On made-up samples the same rules scored 96.6%; that number measured the author, not the attackers.
- **The lexical ceiling is 91.2%:** on 91% of real phishing URLs no URL rule fires at all, and on another 6.3% the rules fire too weakly to flag. Reading the address cannot catch these. Phishing on its own domain (84,106) and on platforms where anyone can publish (41,461: Google Docs, pages.dev, SharePoint, ...) is almost all invisible to it. IP-address phishing is the exception: 73.7% caught.
- **False alarms:** 0.3% on 166,265 legitimate URLs, but those are almost all home pages (PhiUSIIL's legitimate URLs and Tranco are domains). On the owner's own browsing (87 URLs with real paths) **9.2% were flagged** (4.7% to 17.1%): `url.login_path` 5, `url.parser_tricks` 5, `url.open_redirect` 3, i.e. ordinary sign-in pages and redirect parameters. A sample that small proves little, but it points the same way: the real false-alarm rate while browsing is far above 0.3%.
- **Fitted weights:** on the test split recall went from 2.5% to 2.7% (only `url.ip_literal` changed, 0.3 to 0.45), false alarms unchanged. Below the rule for adopting (intervals must not overlap), so **not adopted**. Weights cannot move a ceiling: the misses carry no signal to weigh.
- **What this means for the plan:** the list feeds (OpenPhish, PhishTank) catch a URL only once it is listed, and the URL rules almost never catch it before. Detection of a new phishing page has to come from looking at the page (URL detonation, visual brand matching) and from context (who sent it, what the message asks). Those are the next milestones. Before that, the three rules behind the false alarms on real browsing need fixing.

## Fix: the false alarms on the owner's browsing (URL ruleset 1.1.0, 2026-11-10)

Two causes, both in the rules, fixed where the rule decides (not per site):

1. **Double encoding in a query value** (5 sign-in pages carrying `next=%252F...`): `url.parser_tricks` now counts double encoding only in the path, where it hides from path filters. An off-site address hidden by double encoding is still caught by `url.encoded_target`.
2. **Share dialogs counted as redirects** (4 LinkedIn share links): `url.open_redirect` skips a share dialog on an official domain (`share_paths` in `rules/url/lists.toml`: `/shareArticle`, `/sharing/share-offsite`, `/sharer/sharer.php`, `/intent/tweet`, `/feed` with `shareActive` ...). Real redirectors on the same sites (`linkedin.com/redir/redirect`, `google.com/url`) and look-alike share paths on other hosts are still flagged; the allow-list still does not vouch for a share dialog (`tests/unit/test_e1_false_alarms.py`).

Measured on the same data: false alarms on the owner's browsing 9.2% to **0 of 92** (0.0%, 0.0 to 4.2%); real phishing caught unchanged at 2.5%; false alarms on Tranco and PhiUSIIL unchanged; the synthetic dev set unchanged (84 TP, 0 FP). 92 URLs is still a small sample: more of the owner's browsing, or Chrome's, would make the false-alarm figure firmer.
