# M2: Email and file inspection (PROPOSED, awaiting approval)

**Goal (SPEC §15 phase 2, CLAUDE.md M2):** from representative EML, HTML, PDF, image and archive samples, produce evidence-backed phishing indicators. Every URL found goes through the M1 engine. Hostile input is parsed with hard limits, in a sandbox, with no network.
**Not in M2:** live mailboxes (M5), threat-intel providers (M3), following any URL (the resolver stays off), any LLM, Office documents.

## Before M2 starts (needs you)
1. **Sign off ADR-008, the parser sandbox.** It is the critical path. Proposal: a restricted Windows process (Job Object limits, AppContainer or restricted token, no network) speaking a narrow stdin/stdout protocol, with the same worker run in a Linux container in CI for bomb fixtures.
2. **ADR-007 (evidence encryption) stays unsigned?** Then M2 persists hashes only, as M1 does: no message text, no URLs, no attachment bytes. Emails are the most sensitive data in the project; I would not store them without it.
3. **Approve dependencies.** Licences below are from memory and I will verify each from official sources before adding it.
   | Need | Proposal | Note |
   |---|---|---|
   | MIME | stdlib `email` | none |
   | HTML | `beautifulsoup4` (MIT, SPEC §4) | with the stdlib `html.parser` |
   | PDF | `pikepdf` (MPL-2.0) | **not PyMuPDF**: SPEC §4 names it, but it is AGPL-3.0 or commercial, which may not fit how MIRAGE is distributed. Your call |
   | Images, QR | `Pillow`, and OpenCV's built-in QR detector (`opencv-python-headless`, Apache-2.0) | avoids `pyzbar`'s native DLL |
   | OCR | Tesseract (Apache-2.0) via a thin wrapper | native install plus Polish language data; heaviest item |
   | Archives | stdlib `zipfile` and `tarfile` | our own limits; 7z and RAR out of scope |
   | Test fixtures | a small QR generator, dev only | PDFs and bombs generated at test time, bounded |
4. **Split M2?** I recommend two commits-worth of scope that can ship separately:
   - **M2a, text formats:** MIME, headers, HTML, hidden links, attachment inventory. Pure Python, no OCR.
   - **M2b, binary formats, sandboxed:** PDF, images with QR and OCR, archives, HTML smuggling.
   If you want everything in the sandbox from day one, M2a waits for ADR-008.

## Modules
- `core/email/` (new): bounded MIME walk; headers: From, Reply-To and Return-Path mismatch, Received chain oddities, SPF/DKIM/DMARC read from the receiving server's `Authentication-Results` (no DNS lookups, so offline); attachment inventory with SHA-256 and type by file signature, not by name or declared type.
- `core/documents/` (new): HTML analyser (display text vs real destination, invisible or zero-size links, image links, forms posting off-site, `javascript:` and `data:` links, meta refresh); PDF (URI annotations, JavaScript and Launch actions, embedded files); images (QR decode, OCR text); archives (listing and limits, never extracting to disk).
- `rules/email/`, `rules/document/`: rules as in M1: pure functions, a weight, an ATT&CK tag, a positive and a negative fixture each. Candidate tags: T1566.001 (attachment), T1566.002 (link), T1204.002 (malicious file), T1027.006 (HTML smuggling). **Only four ATT&CK IDs have been verified so far; I will check these on attack.mitre.org before use.**
- `core/risk/`: the same scoring model. One feature alone never makes anything malicious (SPEC §6); a PDF with a URI is not an alert by itself.
- API and CLI: `POST /v1/emails/analyze` (raw message bytes, capped, token-authenticated) and `python -m core.cli analyze-eml <path>`.
- Contracts and schema: `EMAIL` and `FILE` artifacts already exist; `extracted_urls` finally gets used (host and hash, no URL text); a per-message report that lists parts, extracted URLs and signals with their location (for example `part 2.1`). Any change to the verdict model needs your approval.

## Hard limits (all configurable, all tested)
Message size; MIME depth and part count; header count and length; HTML size, element count and nesting; PDF page and object counts; image pixels (decompression bombs); OCR time and pixel cap; archives: depth, entry count, total uncompressed size and ratio, encrypted entries reported not opened, path-traversal names reported not used. Nothing is written to disk. The worker has no network. A limit hit gives UNKNOWN with the reason, never BENIGN.

## Security implications
Hostile documents are the top threat in the model (T1). The sandbox is what makes this safe; without ADR-008 I would run only M2a, in-process with limits, and say so. OCR and QR output is attacker-chosen text: it is analysed offline and never fetched. Logs carry hashes and counts, never content.

## Acceptance criteria
- Representative EML, HTML, PDF, image and archive samples give indicators, each tied to evidence and a location.
- At least 30 malformed-MIME cases and bomb fixtures (zip bomb, nested archives, decompression-bomb image, deep HTML, 10,000-part MIME, huge PDF object count) finish within time and memory limits and never crash the process.
- Determinism, network-blocked tests, PostgreSQL tests and a clean-checkout run, as in M1.
- A labelled message corpus (synthetic, at least 100 messages, dev/holdout/reserve, hashes pinned) with the same honest reporting: Wilson intervals, abstain rate, per-rule precision, and the statement that synthetic positives measure rule correctness.

## Risks
- The Windows sandbox is the hard part and the least familiar to me: expect a spike before committing to the design.
- Synthetic emails are written by the rule author; the same overfitting caveat applies and is larger for messages than for URLs.
- OCR accuracy, and Polish text, are unmeasured.
- The AGPL question for PyMuPDF.
