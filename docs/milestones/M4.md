# M4: Windows agent and browser extension

**Status (2026-11-05): complete and verified, pending review (see Results at the end).** Approved by the owner with the recommended answer to each of D1 to D8. The first step is a set of short **spikes** (several facts below are unconfirmed and decide how parts are built); their results are reported, and recorded at the end of this file, before the parts that depend on them.

**Goal (CLAUDE.md M4, SPEC §10, §12, §15 phase 4):** MIRAGE keeps watching with no UI open. A .NET agent watches the download folder, hashes and types new files, sends them to the local core and shows a notification; an Edge/Chrome Manifest V3 extension sends navigations and downloads to the agent through Native Messaging and shows a warning page for bad verdicts. **Done when:** it works with the UI closed, blocks a test phishing URL, and flags a test file.
**Not in M4:** quarantining, moving or deleting files (M6, the response engine), live mailboxes (M5), the console (M6), an installer or machine-wide service (M7), any LLM, Firefox or Chrome-specific verification (Chrome is not installed here).

## Design

- **Layout** (CLAUDE.md): `agent/` (.NET solution: `Mirage.Agent` worker, `Mirage.NativeHost` stdio bridge, `Mirage.Agent.Tests`), `extension/` (TypeScript MV3, `src/`, `test/`, built to `dist/`), core additions in Python.
- **Agent.** Watches the configured folders (default: your Downloads known folder) with a `FileSystemWatcher` (small filter, 64 KB buffer, an Error handler that triggers a re-scan, a start-up re-scan of files newer than the last run). Temporary names (`.crdownload`, `.tmp`, `.part`) are ignored until renamed; a file counts as ready when its size stops changing and it opens for reading. It then computes SHA-256 while reading (one read: what is hashed is what is sent), identifies the type by signature (a table shared with the core's `filetype.py` and tested against the same fixtures), reads the Mark of the Web if present, and queues an event. Reparse points outside the watched folder are not followed.
- **Queue.** An append-only spool on disk, at-least-once, idempotent by hash+modified time, bounded (an overflow drops the oldest and records that it did). The spool holds hashes, sizes, types, extensions and the origin **host**; never a URL. URL checks are never queued (the navigation is over by the time the core is back).
- **Core additions.** `core/files/engine.py` builds a single-attachment context and runs the existing attachment and file rules (dangerous extension, double extension, type mismatch, macro, archive contents, PDF JavaScript, ...), scored with the message config; a file is never BENIGN. A `inspect_bytes` sandbox operation for standalone files. `POST /v1/files/analyze` and a metadata-only check; `POST /v1/overrides` writes the audit record. Storage stays hash and host only.
- **Native host.** A small console program: the browser starts it with the caller's origin as its first argument; it refuses any origin but the pinned extension ID, then bridges frames between stdio and the agent's pipe. Frame sizes are capped, JSON is parsed strictly, unknown message types are refused. The extension ID is pinned with the manifest `key` field and the same ID goes in the host manifest's `allowed_origins`.
- **Extension.** A service worker holds one `connectNative` port (reconnecting with backoff). Top-frame `onBeforeNavigate` and `onCommitted` URLs (so redirect landings are checked too), and downloads, go to the agent as small versioned messages; verdicts come back with reasons. A verdict cache keyed by the hash of the exact URL string (no URL-parsing parity needed) lives in `storage.session`. `chrome://`, `edge://`, extension and `file:` URLs are skipped; InPrivate is not enabled. A toolbar popup shows whether the agent is connected.
- **Latency.** The agent answers from the local rules and the list feeds. The core runs with a short provider deadline for this path (`MIRAGE_INTEL_DEADLINE`, 0.5 s) so a slow provider never delays a block; late answers still warm the cache. Navigation latency (extension to verdict) is measured and reported, not promised.
- **Notifications.** A toast for a SUSPICIOUS or MALICIOUS file and for a block, from the agent (not elevated). If toasts are unavailable the event is still logged and recorded.
- **Logs.** The agent logs hosts and hashes only, with the same redaction rules and tests as the Python side.

## Security implications

New attack surface: a pipe, a native host, a browser extension with `nativeMessaging`, and a process that reads every file you download. Controls: the pipe is current-user only with a handshake secret; the host checks the browser-supplied origin; sizes and message types are capped; the extension has no content scripts and cannot be driven by a web page (the override is accepted only from the extension's own page after a real click); URLs travel loopback-only and are never written down; a hostile file name, symlink, junction, oversized or still-growing file is handled by tests; the agent runs unelevated. What a malicious web page can learn is limited to whether the extension is installed if its warning page is web-accessible (fingerprinting, noted).

## Acceptance criteria

1. **UI closed:** with only the agent and the core running (started as at logon, no console window, no browser needed), a synthetic test file dropped in the watched folder reaches the core, gets a verdict, produces a notification attempt and a stored record, within a measured time.
2. **Blocks a test phishing URL:** in Edge with the extension loaded, a synthetic phishing URL served from this machine (a `.localhost` name that matches the URL rules) ends on the warning page; "continue anyway" works for 15 minutes and leaves an audit record; an ordinary page is untouched; with the agent stopped the page loads and the badge says "not protected". (If Spike 1 fails, this is demonstrated at the message level in tests and checked once by hand.)
3. **Flags a test file:** a synthetic archive holding an executable-named entry and a PDF with a JavaScript action each produce SUSPICIOUS or worse with signals; a plain text file does not.
4. **Hostile input:** malformed, oversize, unknown-type and wrong-origin messages are refused at the host and the pipe; a wrong handshake secret is refused; file names with control characters, a junction pointing outside the folder, a file that grows while being read, and a burst of 1,000 files do not crash the agent or lose events (or the loss is recorded).
5. **Resilience:** core down, then back: queued file events are delivered once; agent restarted: no duplicates, no missed files since the last run; watcher buffer overflow triggers a re-scan.
6. Unit tests (xUnit, vitest with a fake `chrome`), core tests, the existing suites, a clean-checkout run, lint for all three languages, docs and limitations.
7. **Not claimed:** that it works in Chrome, as an SCM service, elevated, or with another security product running; that a toast was *seen* (I can only check the attempt; you confirm on screen); the first-visit race is closed.

## Risks

- **Side-loading into branded Edge may be blocked**; then automated end-to-end proof of the browser half is not possible without a download you must approve.
- **The first request to a new URL can beat the verdict** (D4). Instant blocking needs the optional host permission.
- A service worker that dies mid-check, a host that crashes, or a toast that never shows are failure modes I can test for but not rule out on every Windows configuration.
- `FileSystemWatcher` can drop events; the re-scan covers it but is a safety net, not a guarantee.
- Three languages (Python, C#, TypeScript) triple the lint and CI surface; CI has still never run.
- This is the largest milestone so far; the spikes may change the order or the scope, and I will say so before building.

### What changes in the plan because of this

- **D7:** drop `Microsoft.WindowsAppSDK` (large, licence unverified, unneeded); add `System.Security.Cryptography.ProtectedData`.
- **D8:** settled; installed Edge is the test browser.
- **D3:** the extension needs no `tabs` permission. Instant blocking needs host access (granted from the options page); without it the first visit reaches the server, as D4 says. Tests of the instant path run headful.
- **Host design:** a native executable (not a `.cmd` wrapper as in the spike), exit on stdin end-of-file, check the origin argument, **never crash or block**: reply `agent_unavailable` within a few hundred milliseconds.
- **Agent design:** Mark of the Web and browser download URLs are read for host and hash only. File events are joined with extension download events by path and time.
- **Unverified and carried into the acceptance list:** service-worker idle behaviour with a port (manual), remote pipe clients, a visible toast banner (you), the real optional-permission prompt (you), Chrome.

## How to try it by hand

There is no GUI yet (the console is M6). You test through Edge and the Downloads folder.

1. Build: `dotnet build agent\Mirage.slnx`, then `cd extension; node build.mjs`.
2. Tell the agent how to start the core: create `%LOCALAPPDATA%\Mirage\agent.json` containing `{ "CoreCommand": "C:\\mirage\\.venv\\Scripts\\python.exe", "CoreWorkingDir": "C:\\mirage" }`. Stop `python tasks.py serve` if it is running (the agent starts its own core on port 8765).
3. `agent\Mirage.Agent\bin\Debug\net10.0-windows10.0.19041.0\Mirage.Agent.exe --install` (start at logon and register the browser bridge for Edge and Chrome; `--uninstall` undoes it; `--status` shows it), then run `Mirage.Agent.exe` with no arguments. It has no window; its log is `%LOCALAPPDATA%\Mirage\agent.log`.
4. In Edge: `edge://extensions`, Developer mode, Load unpacked, `C:\mirage\extension\dist`. Open the extension's Options page and click "Allow instant blocking".
