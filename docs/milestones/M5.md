# M5: Live email (Gmail read-only first, then Outlook)

**Status (2026-11-05): Gmail built and tested against a fake Gmail; the live check with your account is pending; Outlook (M5b) not started.** The owner said to follow M4 with M5 without pausing, so the decisions below carry my recommendation and I built on it.

**Goal (CLAUDE.md M5, SPEC §9, §15 phase 5):** MIRAGE reads a mailbox **read-only**, analyses each new message with the engine from M2/M3 (sandboxed parsing, no mail stored), records a verdict and notifies, and **recovers messages it missed** while it was off. **Done when:** a test mailbox is analysed automatically, and missed events are recovered.
**Not in M5:** moving, labelling, deleting or quarantining mail (M6, a separate explicit capability), sending mail, the console (M6), Outlook before Gmail works (M5b), any LLM.

## What I found out first (official Google documentation, read 2026-11-05)

| Topic | Confirmed | Not stated on the pages read |
|---|---|---|
| Incremental sync | Keep the `historyId`; `history.list` from it. Records are "typically available for at least one week" and may be "significantly shorter". An out-of-date `startHistoryId` returns **HTTP 404** and the client must do a full sync. `historyTypes` includes `messageAdded`; `labelId` filters; `maxResults` 100 (max 500); pages by `nextPageToken` | Whether `messageAdded` also covers mail that arrives already read |
| Message content | `messages.get` with `format=raw` returns the whole RFC 2822 message base64url-encoded in `raw` | A size limit for the response |
| OAuth for desktop apps | Authorization-code flow with a **loopback redirect** (`http://127.0.0.1:port`), **PKCE** (use `S256`), token endpoint `https://oauth2.googleapis.com/token`; the client secret is "optional" in the token request and desktop apps "cannot keep secrets confidential" | Whether `access_type=offline` is needed for installed apps (the page says refresh tokens are always returned to them) |
| Refresh-token life | An external app whose publishing status is **"Testing" gets refresh tokens that expire in 7 days**. Tokens also die when access is revoked, after six months unused, and **when the user changes their password if the token has Gmail scopes** | Any separate rule for unverified apps |
| Scope | `https://www.googleapis.com/auth/gmail.readonly` is a **restricted** scope (restricted-scope verification for public apps); `format=raw` is not allowed with the narrower `gmail.metadata` scope | |
| Quota | `history.list` 2 units, `messages.list` 5, `messages.get` 20 (**60** for `raw`); **6,000 units per minute per user** ≈ 100 raw fetches a minute | |

## Decisions I need from you (my recommendation is what I build)

| # | Decision | Recommendation |
|---|---|---|
| **D1** | **Scope.** | `gmail.readonly` only. It is the narrowest scope that can return the raw message; the narrower `gmail.metadata` cannot. No modify scope in M5 (that is M6, explicit). |
| **D2** | **Where the poller lives.** | In the **core** (Python), as a background task started with the API, so the existing engine, storage and audit are used directly. It calls Google over HTTPS with `httpx` (already approved). **No Google client libraries**: the OAuth flow here is two requests, and the libraries are large. This is the only part of MIRAGE that talks to the Internet on the user's behalf; it talks only to `accounts.google.com`, `oauth2.googleapis.com` and `gmail.googleapis.com`. |
| **D3** | **Tokens at rest.** | The refresh token is stored encrypted with **Windows DPAPI (current user)** through `ctypes` (no dependency), in the data folder, never in the database, an env file, logs or git. The OAuth **client id** (and secret, if Google issues one for the desktop client) is yours: read from environment variables, placeholders in `.env.example`. |
| **D4** | **What is stored.** | Unchanged from M2: the verdict, signals, hashes of URLs, domain and sender domain. **No message body, no subject, no addresses, no raw message is written anywhere**; the raw bytes live in memory for one analysis and go to the sandbox. The Gmail message id is stored as a SHA-256 (it is the idempotency key). |
| **D5** | **Sync.** | First connect records the current `historyId` and looks back **N days** (default 2, 0 to disable) with `messages.list` so a fresh install does not read years of mail. Then poll `history.list` (`messageAdded`, label `INBOX`) every 60 s. A 404, a gap, or a restart after a long absence triggers a bounded re-list of the last N days, de-duplicated by message-id hash. Fetches are rate-limited to stay well under the per-user quota and back off on 429/5xx. |
| **D6** | **What happens on a bad verdict.** | A record, a toast ("suspicious email from `<sender domain>`", no subject, no address) and the verdict in the API. **Nothing is changed in the mailbox.** |
| **D7** | **Outlook.** | **M5b**, after Gmail is proven: Microsoft Graph `Mail.Read`, delta queries, same poller interface. It needs an Azure app registration of yours. Not started until you say so. |
| **D8** | **Testing without your account.** | The Gmail client, sync and recovery are built and tested against a **fake Gmail server** (httpx mock transport) that follows the documented shapes, including 404 on an old history id, 429, paging, a message deleted before it is fetched, and hostile payloads. This proves the logic, **not** that Google accepts the requests: the live check is a short checklist for you (below). |

## Design

- **`core/mailbox/`**: `oauth.py` (PKCE + loopback listener bound to 127.0.0.1 only, state check, one-shot), `tokens.py` (DPAPI file), `gmail.py` (typed client: `list_recent`, `history`, `get_raw`; strict response models; every response size-capped), `sync.py` (the state machine: connect → backfill → poll; checkpoint = last `historyId` kept in a small state file written atomically; idempotent by message-id hash), `service.py` (runs the loop inside the API process; `status` endpoint; stops cleanly).
- **Analysis path:** the raw bytes go through the existing `analyze_message` (sandboxed MIME/HTML/PDF/image parsing, URL engine, M3 intel under the same egress rules), then `save_email_analysis` with `EventSource.EMAIL`. A mailbox message is limited to the existing 10 MiB message cap; larger ones get a stated UNKNOWN (reason `too_large`), never a pass.
- **CLI:** `python -m core.mailbox connect` (opens the consent URL, runs the loopback listener, stores the token), `status`, `poll --once`, `disconnect` (deletes the token and asks Google to revoke it).
- **API:** `GET /v1/mailbox/status` (connected, last sync time, counts, last error class; no addresses).
- **Failure rules (CLAUDE.md):** an unreachable Google, an expired token or a 404 is a stated state shown by `status` and a toast once, never "no phishing found"; a message that could not be fetched or parsed is recorded as ERROR/UNKNOWN with a reason and retried a bounded number of times.

## Security implications

New: OAuth credentials, a refresh token with read access to the whole mailbox, and a process that fetches mail over the Internet. Controls: read-only scope; token DPAPI-encrypted and never logged (a test searches logs and storage for the token); the loopback listener binds 127.0.0.1, accepts one request with the right `state`, then closes; HTTPS to three Google hosts only (a test asserts any other host is refused); response sizes capped; the raw message is never persisted and never sent to threat-intel providers (only URL hosts under the M3 egress gate, and `MIRAGE_INTEL_EMAIL_LINKS` stays off by default); message ids stored as hashes; logs carry counts, ids-hash prefixes and status classes only.
**Residual risk I cannot remove:** anyone who can run code as your Windows user can ask DPAPI for the token. Revoking access in your Google account (or `disconnect`) is the remedy.

## Acceptance criteria

1. **Automatic:** against the fake Gmail, new messages are analysed within one poll interval with no user action, and each produces a stored verdict with signals (a phishing sample is SUSPICIOUS or worse; an ordinary one is UNKNOWN or BENIGN as the engine decides).
2. **Recovery:** messages that arrived while the poller was stopped are analysed once after restart; an expired `historyId` (404) triggers the bounded re-list; nothing is analysed twice; a crash between fetch and save does not lose or duplicate a message.
3. **Hostile input:** malformed JSON, oversize bodies, invalid base64, a message that vanishes before fetch, 429/5xx storms, an OAuth `state` mismatch, a redirect to a non-loopback address, and a wrong host are all refused or retried with a stated outcome, never a pass.
4. **Privacy:** the database, logs and state file contain no addresses, subjects, bodies or tokens (tested by searching for planted markers).
5. **Read-only:** the only HTTP methods sent to Gmail are GET (asserted on the fake server); the requested scope is exactly `gmail.readonly`.
6. Unit/integration tests, the existing suites, lint, docs and limitations; ADR-017 for the poller and token storage.
7. **Not claimed until you run the live check:** that Google accepts this client, that the consent works for your account, that real raw messages parse, and what a 7-day "Testing" token expiry feels like.

## Risks

- Restricted scope + 7-day tokens make long-running unattended use awkward until the app is verified or the project is an internal Workspace app.
- `history.list` semantics for already-read mail are not documented on the pages I read; the bounded re-list covers it, at a quota cost.
- 60 units per raw fetch limits throughput to about 100 messages a minute per user; a mailbox burst is queued, not dropped.
- I cannot test against the real Gmail until the owner's credentials exist.
