# M6: Response engine and console

**Status (2026-11-05): proposed, not approved.** This milestone moves your files and builds the first screen you can look at, so it waits for your answers to D1 to D8 below (each has my recommendation). Nothing is built yet.

**Goal (CLAUDE.md M6, SPEC §8, §15 phase 6):** turn a recommendation into an action you control. A dangerous file can be **quarantined**; the quarantine is **reversible, idempotent, audited, permission-gated and fail-safe**; a console lets you see what MIRAGE found, approve or dismiss actions, and **restore** anything. **Done when:** quarantine is reversible, idempotent and audited, and restore works.
**Not in M6:** deleting anything (no code path for it at all), email quarantine unless you answer D6 differently, the installer (M7), any LLM, Outlook.

## Design

- **Core (`core/response/`):** `actions` table (id, kind `FILE_QUARANTINE|FILE_RESTORE`, state `PENDING|APPROVED|APPLIED|DISMISSED|FAILED|RESTORED`, artifact/verdict link, file SHA-256, reason code, created/decided/finished times, decided by `user|policy`) and `allowlist` table (SHA-256, expiry, created by). Stores hashes, ids, states, reason codes; **not paths or file names** (those stay in the agent's quarantine folder). Endpoints: list/get events with evidence, list/approve/dismiss/restore actions, allow/unallow a hash, read the audit log. Every state change writes an audit row. State transitions are a small table-driven state machine; an illegal or repeated transition is a no-op with the current state returned (idempotent).
- **Agent (`Mirage.Agent`):** `QuarantineStore` (the mechanics in D4, with fault injection in tests), an action poller (like the mailbox watcher), `FileEvent` → core with the new "file is allow-listed" check, config `ResponseMode: ask|auto`.
- **Console (`console/`):** pages: Overview (agent, core, mailbox state), Events (verdicts with signals and evidence, filter by state), Actions (pending with Approve / Dismiss; applied with Restore), Quarantine (list, restore), Allow list, Audit log. Plain components, no router library, no state library.
- **Verdict model:** unchanged. `applied_response` is written when an action is applied (the field already exists).

## Security implications

New: a component that **moves your files** and a UI that can ask it to. Controls: nothing is deleted by any code path (a test greps the agent and core for delete calls outside temp-file cleanup and fails if one is added); every move is verified by hash before the original goes; every state is recoverable from the quarantine record; the core never receives paths; an approval is an authenticated API call with an action id (not a link a web page could trigger); the console is same-origin with a strict CSP; the agent refuses an action whose file hash no longer matches the one that was judged; links and cloud placeholders are not followed or hydrated (as in M4); `auto` is off by default and only MALICIOUS; restore never overwrites.
**Residual:** an antivirus may act on the same file; a program running as you could read the quarantine folder (it is not encrypted in M6; quarantined files are still dangerous on disk, so they get a neutral name and no execute association, but they are not defanged); the agent being down means pending actions wait.

## Acceptance criteria

1. **Quarantine works and is reversible:** a synthetic malicious file in the watched folder produces a pending action; approving it in the console moves the file, the original is gone, a record and an audit row exist; **Restore** returns byte-identical content to the original path.
2. **Idempotent:** approve twice, restore twice, a duplicate action id, and the agent re-delivering the same action all end in the same single outcome.
3. **Fail-safe:** a locked file, a missing file, a changed file (hash mismatch), a junction/link, a cloud placeholder, a full disk, a cross-volume move interrupted before the original is removed, a crash between copy and verify, and a name clash on restore never lose or overwrite a file, and each ends in a stated state.
4. **Permission-gated:** with the default policy nothing moves until you approve; `auto` applies to MALICIOUS only; SUSPICIOUS is never moved.
5. **Audited:** every approve, dismiss, apply, fail, restore and allow-list change has an audit row with actor, action, hash prefix and result; no path or file name is in the database or logs.
6. **Console:** shows events with evidence, pending actions, the quarantine and the audit log; drives the whole flow in the real-Edge end-to-end test; strict CSP; hostile text (markup in a rule, a file name, a reason) is shown as text.
7. **No delete code path** (tested), unit/integration tests, existing suites, lint for all languages, docs (ADR-018 for the response engine, limitations, threat model), a clean-checkout run.
8. **Not claimed:** email quarantine (D6), a Tauri shell (D1), protection when an antivirus quarantines the same file first, the console on Chrome.

## Risks

- Moving a file the browser or an antivirus still holds open; handled as FAILED with a reason, but real-world timing is untested beyond this machine.
- Two security products acting on one file is untestable here.
- A console in a browser tab is less isolated than a native shell (D1); the CSP and token handling are the mitigation.
- This is the first milestone that can *harm* a user's data if wrong; hence the fault-injection tests come before any real move.
